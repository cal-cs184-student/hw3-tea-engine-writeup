Part 1: Ray Generation and Scene Intersection

Ray generation seeks to transform a normalized location on the camera sensor into a ray in world space going from the origin of the camera through the specified point. It does this with first a transformation matrix that gets the right rotation in world space, then a translation to the origin of the camera in world space. We test for intersection for spheres and triangles To test triangle intersection with a ray, we first find the point where the ray intersects with the plane the triangle is on, which is computed using dot and cross products, the formula is derived by substituting: The ray equation: \[r(t) = o + td\] into the plane equation \[(p - p') · N = 0\] where p is the test point, p' is a point on the plane and N is the plane's normal vector. After plugging in the ray equation for p, and isolating t, we are able to solve for a t-value this way and determine when a ray intersects with a plane. \[t = (p' - o) · N / (d · N)\] Next, we use the point in triangle test on that point to determine if the ray has intersected with the triangle. The point in triangle test is performed by performing cross products with each edge and the vector formed by the start of that edge with the point the camera ray produced earlier, and we check if each of these cross products points in the same direction as the normal of the triangle with another dot product. If these tests pass, we know the point is in the triangle and thus the ray intersects the triangle. To test sphere intersection we follow a similar process with substituting r(t) into the point of an equation describing a sphere. This gives us a quadratic to solve, upon solving we choose the intersection with the smaller t value indicating that it was the one that hit the sphere first.

Part 2: Bounding Volume Hierarchy

At a high level, the BVH construction algorithm is a recursive algorithm that organizes a defined set of primitives (like triangles) into a binary tree for efficient and fast lookups of what a ray can possibly intersect within the scene.

The binary tree that organizes the primitives has inner nodes and leaf nodes. Each node is a BVHNode that can store its bounding box, a left and right attribute that identifies its children BVHNodes and a start and end iterator that represents the start and end of a vector of primitives that are within that bounding box.

In the binary tree there's inner nodes and leaf nodes, where the inner nodes contain the overall bounding box for its children nodes and a left and right attributes for their respective childrenBVHNodes. The crux of the BVH acceleration algorithm though is in its heuristic to decide how to split a list of primitives. Our initial method was to find the longest axis of the bounding box and select the median element of this axis and divide the primitives into the left and right children BVHNodes so that they would be roughly equal between each other.

The heuristic we split on is the size of the bounding boxes on the largest remaining axis at each stage of the BVH. We choose the axis with the largest extent, then find the leftmost primitive and create a bounding box with the primitive which extends the sub-bounding box to as close to splitting the current box in half in the chosen axis (we also add any primitives contained within to be in the bounding box).

Once the binary tree is formed, an intersect method for the bounding boxes helps us recursively traverse the BVH formed binary tree by determining if a ray firsts hits a node's bounding box and with the base case that stops recursion if the BVHNode is a leaf node. When we hit a leaf node we then check intersections with all the primitives within that bounding box (via iterating through the start and end attributes) and report intersection info and whether the ray successfully hit any primitives.

Our performance comparison shows a massive difference between using and not using BVH. For CBlucy.dae rendering with 10 threads, we went from 775.4139 seconds to render down to a mere 0.0746s. This drastic 1000x speedup makes sense, as we averaged only 1.23 intersection tests per ray using our BVH implementation, as opposed to 17022.73 intersection tests without BVH. Similarly, for CBbench.dae rendered in 0.618 seconds using BVH, and 353.3483 seconds with BVH.

Part 3: Direct Illumination

For this part, we had to implement two different versions of the direct lighting function, specifically uniform hemisphere sampling and importance sampling. Both methods aim to provide path tracing with one bounce illumination by providing shading to a pixel where a camera's ray has intersected a primitive. The method in which we perform this is by tracking inverse rays where we fire the rays from the camera and when they intersect with a primitive we determine its shading via the rendering equation (instead of tracking light coming from the light sources):

\[L_o = ∫(L_i(x, wi) * f_r(x, wi, wo) * (N · wi) dwi)\]

Where \(L_o\) represents the outgoing radiance that we want along the camera ray that we had fired.

\(L_i\) represents the incoming radiance from the direction of the incident ray wi, and with the integral integrating over the space with respect to wi we calculate the irradiance of a hit position.

\(f_r\) represents the BSDF (bidirectional scattering distribution function) that defines the "material" of the surface that we are interacting with, and outputs a ratio of how much radiance from the incident ray is turned into outgoing radiance

The final term is the lambert's cosine law term that determines what intensity of shading is emitted, since the light reflected off of a surface is proportional to the cosine of the angle of the surface's normal and the incident ray, or alternatively the dot product between the unit vectors of the surface normal and the incident ray.

Now this integral that we use in the rendering equation is not closed form and cannot be solved quite easily, so as a result we use a method known as Monte Carlo sampling where we sample randomly to approximate the integral.

For our first method, direct illumination via uniform hemisphere sampling, we performed sampling over a hemisphere around our intersection point and randomly sampled directions uniformly over this hemisphere with the goal of approximating the rendering equation integral by adding up the emission values (which are non-zero when intersecting with light sources) and multiplying by our sample "width" = 1/N. Our probability distribution function (p(x)) is uniform in this situation so our probability density function is constant at a 1/(2pi) representing a hemisphere in steridians.

For a second method, we used direct illumination via importance sampling. Importance sampling at a high level uses a different distribution that has useful data to help us better estimate the rendering equation integral, which in this case we use a method of using the direction of lights to better inform which directions an incident ray can arrive at our surface.

The difference from the uniform hemisphere sampling was that instead of sampling randomly and uniformly in a hemisphere, we seek to sample more effectively and remove noise from the overall scene by adding the criteria of sampling only from directions towards defined lights in our scene and the ray between the light and point is not obstructed (known as shadow rays to check whether we are obstructed by another primitive in the light). In this method, our probability density function is defined by the sampler we use given the direction of our hit point and the source of the light which helps us estimate our integral more effectively to highlight areas where sampling is more representative of the true integral.

Uniform Hemisphere vs. Importance Sampling Analysis: Uniform hemisphere direct illumination compared to importance sampling does have some notable visual differences, namely under the same parameters, the pathtracing for uniform hemisphere sampling results in a subtle but noticeable amount of noise in the rendered image likely due to the higher variance that it experiences from the method of randomly sampling in a hemisphere compared to importance sampling's emphasis on certain areas of a distribution. Additionally, importance sampling also loses the glow on the area light, which is the result of the directionality of the method of importance sampling. Overall importance sampling does result in a clearer, more well defined and less noisy image likely due to its decreased variance from the estimations of its integrals.

Part 4: Global Illumination

To achieve indirect lighting we recursively call the function for "more than once bounce", decrementing the depth of the ray upon each recursive call. Each recursive call adds the one_bounce result to the total radiance L_out if the accumulating setting is on. If the accumulating setting is off, it won't add anything until the very end. We use the Monte Carlo formula mentioned in lecture and also referred to up above to sum and weight each bounce result by the probability distribution function, giving the ray an appropriate weight based on how much the intersection point reflects light in that specific direction. The indirect lighting adds greater fidelity and more conveyed realism to the renders as more soft shadows are able to be added as a result of more bounces following subsequently after our initial one_bounce calculation that we used for direction illumination (difference shown in the examples below).

Direct lighting is the same as our previous implementation of one bounce illumination as the path tracing only resolve one bounce per path, and compared to indirect illumination which skips the first bounce and instead only considers the subsequent recursive bounces, you can see that the indirect lighting is far dampened more subtle as these subsequent bounces carry less energy.

The 2nd and 3rd bounce of light show the light reflecting off the wall onto the bunny. This is in contrast with previous rasterization techniques which weren't able to capture these multi-bounce light features, since they rely on local vertex based shading algorithms.

Where each bounce in out global illumination is not accumulated / summed per bounce, and instead as the ray depth increases it shows subsequently darker images since these are paths that are more indirect and thus are "stages" of the path that have bounced and lost energy to the number of ray depth experienced.

Part 5: Adaptive Sampling

Adaptive sampling is a way to reduce the amount of rays needed in order to render a good image. It uses the principle that some pixels can converge very quickly to the correct color, while others might take a lot more samples if they are part of more complex geometry. Thus, it measures the variance of the samples taken so far and terminates the sampling early if it deems that the noise/variance is low enough. Our implementation achieves this by storing a cumulative sum so far (and its square) to be used in the variance calculations. We check the variance using our sums and the formula every samplesPerBatch to avoid having to do these calculations every single color update. We break out of the loop if the desired confidence interval is reached, or we terminate the loop once ns_aa (max number of samples) is reached.
